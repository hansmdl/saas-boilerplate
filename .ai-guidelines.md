1. Adherencia Estricta al Stack Tecnológico
No debes introducir nuevas librerías o tecnologías que no estén especificadas en la sección "Stack Tecnológico y Versiones". Si crees que una nueva librería es necesaria, debes proponerla y justificarla para su aprobación manual.

2. Respeto por la Arquitectura (Monorepo)
El proyecto utiliza un monorepo con Turborepo. La estructura de carpetas es sagrada y debe ser respetada:
apps/web: Aplicación principal de cara al cliente (Next.js).
apps/api: Backend (NestJS).
apps/staff: Panel de administración (Next.js).
packages/ui: Componentes de React compartidos (shadcn/ui).
packages/db: Esquema y cliente de Prisma.
packages/config: Configuraciones compartidas (ESLint, TypeScript, features.ts).
packages/email: Plantillas de React Email.

3. Estándares de Código (Sistema Inmune)
El código que no cumpla con estos estándares será rechazado automáticamente por nuestros sistemas de control de calidad.
TypeScript en Modo Estricto (strict: true): Está prohibido el uso de any. Todo debe estar correctamente tipado.
ESLint y Prettier: Todo el código debe pasar las validaciones de ESLint y ser formateado con Prettier antes de ser considerado completo. No desactives reglas de ESLint.
Rutas y Alias: Debes usar las rutas absolutas configuradas con alias en tsconfig.json.

// ✅ Correcto
import { Button } from '@/components/ui/button';

// 🚫 Incorrecto
import { Button } from '../../../../components/ui/button';

Diseño de Componentes:
Utiliza Tailwind CSS para todo el estilizado. No escribas archivos .css o .module.css adicionales.
No uses estilos en línea (style={{...}}) excepto para valores dinámicos calculados.
Construye todos los componentes de UI usando los primitivos de shadcn/ui o siguiendo su misma filosofía.
4. Gestión del Estado
La gestión del estado sigue un patrón claro:
Estado del Servidor (Datos de la API): Usa React Query (TanStack Query) para todo el fetching, caching y mutación de datos.
Estado Global de la UI: Usa Zustand para estados globales simples (ej. estado del sidebar, tema de la UI).
Estado Local del Componente: Usa useState o useReducer solo para estado verdaderamente local y efímero.
5. Pruebas Obligatorias
Toda nueva funcionalidad o componente lógico debe ir acompañado de pruebas unitarias o de integración.
Estructura de Pruebas: Las pruebas deben vivir junto al componente o función, en archivos con la extensión .test.ts o .spec.tsx.
Ejemplo de Prueba de Componente:

// packages/ui/button.test.tsx
import { render, screen } from '@testing-library/react';
import { Button } from './button';
import { expect, test } from 'vitest';

test('renders button with correct text', () => {
  render(<Button>Enviar</Button>);
  const buttonElement = screen.getByText(/Enviar/i);
  expect(buttonElement).toBeInTheDocument();
});

6. Formato de Commits
Todos los commits deben seguir la especificación de Conventional Commits.
feat: (una nueva característica)
fix: (una corrección de un bug)
docs: (cambios en la documentación)
style: (cambios de formato)
refactor: (refactorización de código)
test: (añadir o corregir pruebas)
chore: (cambios en el build, configuración, etc.)
7. 🔐 Seguridad y Buenas Prácticas
La seguridad es una prioridad.
No exponer secretos: Nunca incluyas claves de API, tokens o cualquier credencial directamente en el código fuente. Usa siempre variables de entorno (.env).
Validación de Entradas: Valida y sanitiza todos los inputs provenientes del cliente en el backend usando Zod a través de DTOs (Data Transfer Objects) o pipes en NestJS.
Protección de Endpoints: Todos los endpoints sensibles en la API deben estar protegidos por guardias de NestJS (JwtAuthGuard, RolesGuard, etc.) para verificar la autenticación y autorización del usuario.

## 🚀 CI/CD y Flujo de Despliegue

El pipeline de CI/CD configurado en **GitHub Actions** es el guardián de la calidad del código. En cada `push` o `pull request`, se ejecutarán las siguientes validaciones automáticas:

- Formato de código (`Prettier`)
- Análisis estático (`ESLint`)
- Comprobación de tipos (`TypeScript`)
- Ejecución de todas las pruebas (`Vitest`)

**Un `pull request` solo podrá ser fusionado y desplegado a producción si todas estas verificaciones pasan con éxito.**
